Diagnose the deployment problem for: **$ARGUMENTS** (if empty, ask me which PR, preview, or production deployment looks wrong).

**Read-only. This command never deploys, promotes, rolls back, removes, or mutates env** — and never passes `--token` to anything (it overrides the environment and leaks into the process list; use `vercel login` or `VERCEL_TOKEN` in your shell). Deployment happens only through the repo's Vercel Git integration. The Bash guard hook is the enforcement point; the settings deny list is belt-and-braces. **No ⏸ gate and no `/quality-gate` run** — this command changes nothing, though step 3 does build locally.

Delegate to `deploy-doctor`, which works this runbook:

1. **Locate the deployment.** From a PR: `gh pr checks <n>` and `gh pr view <n>` for the check/preview links. From a URL: use it directly. The read-only Vercel CLI (`npx vercel list`, `npx vercel inspect <url>`) is **optional and opt-in** — it needs `vercel login` or `VERCEL_TOKEN` and is allow-listed only in your machine-local settings; if it isn't available, say so and work from `gh` and the dashboard links instead.
2. **Read the *build* logs** — `npx vercel inspect <deployment-url> --logs`. Note that `vercel logs` shows **runtime** logs, which this fully static site does not produce; don't confuse the two. Quote the first real error, not the last line.
3. **Reproduce locally** — on the same Node major the project declares: `npm ci && npm run build` (locally: `if [ -n "$CI" ]; then npm ci && npm run build; else nice -n 19 npm ci && nice -n 19 npm run build; fi`; never in CI, never swallow the exit code). Confirm `node -v` and the project's declared Node version first, and re-derive the branch and commit the deployment was built from (`git rev-parse --abbrev-ref HEAD`, `git log -1`) — never assume.
4. **Work the common-cause checklist:** lockfile drift (a dependency in `package.json` not reflected in `package-lock.json`, or an install that used `npm install` instead of `npm ci`); type errors that a local `next build` skipped but the gate's `typecheck` catches; **case-sensitive import paths** (Linux builders, case-insensitive local filesystem); the declared Node version vs the Vercel project setting (**Vercel does not read `.nvmrc`** — the `engines.node` field and the project setting are what matter; verify the project's actual setting at use-time); a missing environment variable; a per-CVE deploy block (remediate by upgrading the dependency, never by opting out); an image transformation quota rejection on new images.
5. **Check the deployment's own settings at use-time, don't assume:** Deployment Protection level (a "broken" preview is often just an authentication wall), the Node version, and system-environment exposure. Never check indexability on a preview — previews are marked no-index by design, as are outdated production deployments.
6. **Recommend a remediation.** The default is **revert the PR** (`git revert` + a normal PR → the Git integration redeploys). Document, but never perform, the Instant Rollback path: it is a human, dashboard-level action, it only goes back one deployment, and **it turns off automatic assignment of production domains** until it is undone — a trap worth stating explicitly whenever you mention it.

**Output:** symptom → where the deployment is → the first real build error (quoted) → local reproduction result → root cause (or the top two candidates with the evidence separating them) → **recommended remediation, as commands for me to run or a PR to open** → what you could not determine from here (dashboard-only settings, org/plan limits, anything needing credentials). If the root cause is a code defect, hand it to `/fix`; if it's a dependency or toolchain issue, hand it to `/upgrade`.
